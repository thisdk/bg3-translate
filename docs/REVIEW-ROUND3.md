## 1. 这轮是怎么做的（可复核的纪律）

- **冻结基线**：开工前记录 `HEAD`、工作区 hash 与 6 道门禁的真实输出，之后每个结论都对着基线证伪。
- **五个角色，写范围互不重叠**：四位审计者分别负责
  `crates/**/formats + pak`、`crates/**/translation + types`、`src/**`（前端）、
  `src-tauri + config + glossary + scripts + CI + 文档`；
  第五位是**独立红队/验证者**，全程只读仓库（唯一允许写的是它自己的报告），
  既做「先于 writer 的独立发现」，也做「事后对集成结果的证伪」。
- **硬性质量标准**（对每个 writer 一致）：
  1. 每条结论必须附**实际执行过的命令 + 真实输出**，没跑过的一律标「未验证」，禁止「应该没问题」；
  2. 只有在**先写出一条失败测试/探针复现**之后才允许改生产代码，修完必须给出「修复前红、修复后绿」；
  3. 新回归测试会被独立验证者做**变异实验**（把修复改回原样看是否变红），不会变红的判为**无效回归测试**；
  4. 不许删除或削弱任何现有测试、不许放宽门禁（`-D warnings`、`continue-on-error` 一律禁止）、
     不许新增依赖、不许在生产路径新增 `unwrap/expect/panic/#[allow]`。
- **Lead 的集成编辑**（不在任何 writer 报告里，已单独交给验证者复核）：
  1. 截断流的报错文案补上「下一步怎么做」；

## 2. 修了什么

### 2.1 高危（7 条）——会静默损坏用户的产物

| # | 现象 | 后果 | 归属 |
| --- | --- | --- | --- |
| 1 | `content_list` 写回把正文里的**字面** `< br >` 当成真标签写出去 | 整份本地化文件变成**非法 XML**；**零译文、纯读一次再写回就触发** | formats F-01 |
| 2 | 标签**属性值**里的裸 `>` 把标签从中间劈开 | 同上（非法 XML） | formats F-02 |
| 3 | 伪结束标签 `</ b>`（斜杠后带空格）被当成合法结束标签 | 同上（非法 XML） | formats F-03 |
| 4 | 不闭合空元素 `<br>` 被原样写出 | 同上（非法 XML） | formats F-04 |
| 5 | 流式响应被**截断**（`finish_reason=length`，或既无 `[DONE]` 也无 `finish_reason` 就断流）被当成成功译文 | 半截译文发 `Done`、被写进 PAK，**静默内容缺失** | engine F-02（红队 R-01） |
| 6 | 翻译进行中点「完成翻译，去打包」**没有任何闸门** | `translating` 状态的半截流式文本被写进 PAK | frontend F-20 |
| 7 | 一轮结束后**迟到的 `delta`** 会把条目重新点成 `translating` 并追加文本 | 幽灵译文照样进 PAK | frontend F-21 |

第 1~4 条的根因是同一个：**标签识别靠「猜名字」而不是真解析**。
修法是引号感知的 `scan_tag_end` + 用 `quick-xml` 做真解析校验；
同时补了「宽容度不能收紧」的正向用例（`<br/>`、`<br />`、单引号属性、属性换序仍按真标签保留），
避免抓漏报时把正常译文的标签误伤成普通文本。

第 5 条以前**完全丢弃 `finish_reason`**，所以「服务端明说自己没输出完」这件事根本没人看。
现在两种截断信号都判失败：走既有网络重试 → 仍失败则条目落 `error`、写回退回原文，
并配了 4 条正向用例（`stop`、只给 `finish_reason` 不给 `[DONE]`、未知收尾标记、正常 `[DONE]`）防止误杀正常网关。

### 2.2 中危（14 条）——越权、丢数据、防御缺失

- **前端可控字符串逃出工作目录**（影响面最大的一条）：
  `write_file_entries` 直接信任前端传来的 `work_dir` / `file_name`，而 core 侧只做纯 `join`，
  于是 `../../evil.loca` 与绝对路径都能写到工作目录之外。
  **在命令层与 core 层各修一次**（纵深防御）：`file_name` 过 `safe_output_path`，
  `work_dir` 必须等于 `open_mod` 记在 `AppState` 里的那个目录，并且**用记录值当根目录**。
  → formats F-08、shell F-01（= 红队 R-03）
- **写回丢条目 / 丢 key**：`content_list` 与 `.loca` 的写回是「按提交列表重建整个文档」，
  磁盘上已有、本次没提交的条目会被**永久删除**。 → formats F-05 / F-06
- **已有中文被英文原文覆盖**：MOD 自带中文时，只要用户勾上英文文件（或点「全选」），
  写进 `Localization/Chinese/x.xml` 的未翻译条目会退回英文原文，把已有中文冲掉。
  现在写回目标已存在时先读底稿做 contentuid 级合并。 → frontend F-28（= 红队 R-05）
- **压缩炸弹**：`extract_zip_to_find_pak` 原本**没有任何上限**，65 KB 的 zip 24 ms 就能写出 64 MiB。
  现在有四层上限（声明单条目 / 声明总量 / **实际写入字节** / 条目数），
  取值刻意宽松（6 GiB / 16 GiB / 20 万）以免误伤真实的 4K 材质 MOD。 → formats F-10（= 红队 R-04）
- **保真校验漏掉标签属性名**：写回会把**模型输出的标签文本原样**写进 PAK（原文标签不会被恢复），
  而校验只看标签名序列 —— 于是 `<LSTag Type="Spell">` 被模型写成 `<LSTag 类型="Spell">` 或 `<LSTag>`
  照样判「保真」。现在**属性名多重集必须一致**（顺序不计、大小写敏感），属性**值**继续放宽
  （那是玩家可见文本，必须允许翻译）。 → engine F-01（= 红队 R-10）
- **XML 非法控制字符落盘** → 整个 `.xml`/`.lsx` 变非法文件。 → formats F-07
- `safe_output_path` 放行尾随点/空格片段（`".. "` 在 Windows 上会被规整成 `..`）与 NUL 字节。
  → formats F-09 / F-13
- `.lsx` 重复条目产生两个相同替换区间 → 用失效偏移二次替换把值写坏。 → formats F-11
- `walk_files` 跟随符号链接、`repack` 会把工作目录**之外**的文件打进 PAK。 → formats F-14
- 前端另外 4 条中危：上一轮迟到 delta 污染新一轮（F-22）、卸载/切 MOD 后旧一轮命中新 MOD 同 id 条目（F-23）、
  每次新增勾选都重读全部文件并用磁盘内容**丢掉用户编辑与已翻译结果**（F-24）、
  手工保存的译文被 `done` 覆盖、被收尾回滚清空（F-25）。

### 2.3 低危与信息（16 条）

按主题归纳（逐条明细见各报告 §2）：

- **协议与错误处理**：错误信息双重前缀「大模型调用错误: 大模型调用错误: …」；
  401/403/404 这类确定性失败也退避重试 4 次（现在是 408/425/429/5xx 才重试）；
  `baseUrl` 带 query 时拼出废地址；`temperature: NaN` 序列化成 `"temperature": null`；
  `contains_cjk` 漏 CJK 扩展 F/G/H/I 区。
- **内存与边界**：SSE 解码器缓冲原本无上限（服务端不发换行就能持续吃内存），现在有单行/单事件上限。
- **术语表**：「首尾带非 `\w` 字符」的术语（如 `'Brake' Lever`）因为 `\b..\b` **永远不命中** ——
  真实 19,524 条术语里有 **266 条**受影响；现在按首尾字符决定是否加 `\b`。
- **配置**：`BG3_TRANSLATE_HOME="   "` 被当成合法目录（会在 CWD 建一个空格目录）；
  「数据目录创建失败 → 回退临时目录」这条承诺此前**零测试**，现在补上。
- **产物一致性**：`<content>` 原本没有 `version` 属性，写回凭空补出 `version=""`。
- **前端**：文件对话框 reject 变成 unhandled Promise rejection（用户看不到任何反馈）；
  进度条没有 `role="progressbar"` / `aria-value*`，屏幕阅读器读不出进度。
- **门禁自身**：`check_ipc_contract.py` 原本只查**命令名**，参数名写错、结构体字段漏一个都拦不住；
  现在从 4 项扩到 **10 项**（命令名 + 参数名三处一致 + 7 个结构体与事件载荷逐字段对齐 `types.ts` +
  版本号含 `Cargo.lock`），并用 10 组变异验证每项检查真的会 `exit 1`，**原有检查一项未删**。

验证者全程只读仓库，在**冻结 hash** 上独立重跑，writer 的报告对它只是「待验证假设」。

### 3.1 红队 6 条高危/中高危项全部「修复前红 → 修复后绿」

R-01（截断流）、R-02（非法 XML）、R-03（路径逃逸）、R-04（zip 炸弹）、R-05（中文被覆盖）、
R-10（属性名漏报）逐条独立复现，`BEFORE=红 / AFTER=绿`。

值得一提的是验证者**主动更正了自己的口径错误**：R-04 最初用的判据比实际政策更严，
导致误报「仍红」；改用**手工构造的 ZIP64 归档**（声明解压 8 GiB、实际 232 字节、两侧输入完全相同）
之后，修复版在 **179 µs 内、写盘之前**就拒绝了。

### 3.2 跨模块集成面（单范围审计者最容易漏的地方）

| 集成面 | 结论 |
| --- | --- |
| 三层「与磁盘已有内容合并」（core 补回 + 前端底稿合并 + 命令层路径校验） | **幂等**（第二遍写回与第一遍逐字节一致）、**不推翻用户意图**（用户清空译文后不会被磁盘旧值还原）、**无重复无乱序** |
| 写回闸门（前端 `toWritableEntry` + 后端 `has_writable_target`） | 两条前端路径都拦住了 `translating` + 半截 target；后端仍只认 `status == "error"`，列为纵深防御建议（信息级，非阻断） |
| `check_ipc_contract.py` 加强后是否被放宽 | 6 组变异对照：3 组「改前漏检、改后 exit=1」，3 组两边都抓；diff 里删掉的 4 行**全是注释** |
| `scripts/verify.sh` / CI 是否被改弱 | `--list` 与 CI 硬编码期望**逐字符一致**；`.github/**` 零删除、无 `continue-on-error`、`-D warnings` 仍在 |

### 3.3 验证者发现的唯一「防线强度」缺口（已修）

变异实验 M-D 把 `ZipLimits::default().max_entry_bytes` 改成 `u64::MAX`（等于**关掉整条 zip 防线**），
`cargo test` 依然**全绿** —— 因为所有炸弹用例都注入了小上限，没有一条测试盯着默认值。

**这类「防线可以被静默关掉而 CI 不报警」正是本轮最想消灭的模式**，所以已补
`zip_limits_default_stays_bounded`（对默认值设上下界：上界防 `u64::MAX`，下界防小到误伤真实 MOD），
并实测「改回 `u64::MAX` → 立刻变红」。验证者已对这一改动做增量复核。

### 3.4 Lead 发现的 CI 缺口（已修）

本轮新增的 15 条命令层单测（**就是路径逃逸防线那批**）在 CI 里**从来没有被执行过**：
`cargo clippy/check --all-targets` 只**编译**测试不执行，而 `verify.sh` 的门禁清单里没有 `-p bg3-translate`。
等于安全修复的回归防线静默失效。

已在 `tauri-shell`（Windows）job 里加一步 `cargo test -p bg3-translate --lib`。
它**故意不进 `verify.sh`**：`cargo test -p bg3-translate` 要先编译整个 Tauri 壳，
ubuntu runner 上没有 webkit2gtk 连编译都过不去（`docs/ARCHITECTURE.md` 已写明这条边界）。
本机 Linux 实测 15/15 通过；**Windows runner 上能否通过属于「无法验证项」**（见 §5）。

### 4.2 关于「系列变体被误合并」（红队 R-14）

以 `{n}` 占位符结尾的普通句子（如 `Deal {1} damage to {2}`）可能被误判成系列变体，
被拆成残缺片段送去翻译并强制把后缀留在句尾，**损失的是译文质量（中文语序受限）**。

验证者做了定量：**真实样本 41 条原文里 0 例**（既无以 `{n}` 结尾也没有以裸数字结尾的）。
诚实边界：样本只有 41 条且是纯 UI MOD，官方剧情文本（上千条、占位符密集）不在样本里，
**不能据此断言线上频率也是 0**。已确认它**不会弄坏 XML**（占位符完整、产物可再解析）。
维持「低」，记入下一轮 backlog。

### 4.3 本轮明确保留的「有意宽容」

- **标签属性值不参与保真校验**：属性值是玩家可见文本（`Tooltip` 之类），必须允许翻译。
  放的是**值**，不是**名** —— 属性名现在必须逐个对上。改这条之前请先读 `fidelity.rs` 头部的理由。
- **完全不发 `[DONE]`、也不发 `finish_reason` 的第三方网关现在会被判失败**。
  它和「连接被中途掐断」在客户端不可区分，而「宁可失败也不要静默丢内容」。
  以前这类网关能用，是因为半截译文被当成成功写进了 PAK。报错文案现在会告诉用户下一步怎么做。

## 5. 无法验证项（如实列出）

| 项 | 原因 |
| --- | --- |
| repack 后的 PAK 在**真机 BG3** 里能否加载 | 无法运行游戏；只能用产物的 XML/LOCA 语义与真实样本往返推断 |
| 真实 LLM API 的端到端行为 | 没有 key；所有网络行为用注入的假实现 + 直接喂字节给 SSE 解码器验证 |
| Windows 专有行为：保留设备名、`\\?\` 前缀、大小写不敏感、CI 新增步骤能否通过 | 本机是 Linux；测试里用 `cfg!(windows)` / `#[cfg(unix)]` 做了分支，但只能静态判断 |
| `release.yml` 的 4 段 PowerShell | 本机没有 `pwsh` |
